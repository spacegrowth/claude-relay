🚦 relay

Several Claude sessions.
One of them is in charge.

A Claude Code plugin. The lead session plans the work and hands it to executor sessions in their own terminal tabs. It reads every diff. You make every commit.

Delegate. Review. Commit.

Point at the headline and let the picture land: this is five terminal tabs, not five agents in a box. The three verbs at the bottom are the whole talk. Come back to them in the demo.

Concede the overlap immediately: teams also get their own context, their own panes, and direct messaging. The difference is that relay treats the executor as untrusted: it cannot commit, its report is machine-checked against the index, and you approve the plan. Facts for Q&A: agent teams need CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1; teammate model falls through to the lead's; effort is always the lead's; permission modes can't be set per teammate at spawn; a named subagent becomes a teammate without confirmation; one team per session; the lead can't be handed off. Relay handles the last one with /relay:handoff.

why

The best model should be making the decisions, not doing the typing.

The lead is where judgment lives: what to build, whether a diff is really mergeable, when a report is lying to you. Worth an Opus or a Fable.

Renames, boilerplate tests, doc fixes need none of that judgment. That's where the bill goes.

Smaller models aren't worse workers. They need a bounded task: exact files, a finish line a command can check, no "figure out why" in the middle.

Bounded, Haiku lands it. Open-ended, it hands you something that looks right and isn't.

One session plans, delegates and reviews. Cheaper ones do the work in parallel, with a written contract each way.

This is the thesis. Everything else is mechanics. Land "bounded task" here because the model rubric later depends on it.

how it works

The loop

[Lead] your projectplans; splits it into packets
writes one
reads diff + report
commits
1 · packet file: one bounded piece of the plan
3 · report file + staged changes
🚦 4 · relay's Stop hook, in the lead's own session, wakes it
[Exec] topic2 · works in the shared worktree
stages, never commits
writes the report

The wake isn't the executor calling you. It's relay, on your side, watching the report path while you're idle, then announcing 🚦 [relay] — review needed in your session.

Executors can't commit (denied at launch). Leads can't make large inline edits (a hook blocks it). The asymmetry is the design.

Start with the plan, not the arrows: splitting the work into bounded pieces is the lead's judgment and relay never does it for you. That's the callback on the last slide. Then walk the arrows in order. Stress that the wake originates in the lead's session, from a hook: there is no arrow from the executor to the lead except the report file.

First line is the goal. It becomes the executor's opening message and its tab title.

Acceptance is commands, not adjectives. If you can't write the check, you haven't finished thinking.

the contract, inbound

A report, and what you do with it

one-line gist of what happened Status: clean | clean-with-caveats | partial | blocked Risk flags: none UNVERIFIED: none Changed: lib/lead_guard.py, bin/relay, tests/… ## What changed file:line for each ## Verification commands run, counts ## Not done and why

/relay:diff <sid> renders the staged changes as a review page. You read it. There's no substitute.

/relay:verify <sid> checks the report against the index: are the claimed files actually staged, do the counts agree. Its best verdict is COUNTS-MATCH, deliberately not "PASS". The others: MISMATCH, MALFORMED, INCONCLUSIVE.

Then you commit, or you send a fix-list back into the same executor. Executors never commit; you do, with your name on it.

The TL;DR block is machine-read. clean-with-caveats is a stop on purpose: the caveats are the point.

Pair with slide 5. The report format is enforced by the executor's system prompt, not something you ask for each time.

choosing a model

Who gets the packet?

A script could check it's done.

Haiku. Rename sweeps, boilerplate from a shown template, config plumbing. The packet must be tight. If it needs a "why" explained, it isn't Haiku work.

A plausible wrong answer could slip past you.

Opus. Unknown root causes, cross-cutting changes, core logic. Pay for judgment exactly where review can't catch its absence.

Everything else.

Sonnet. Bounded features, bugs with a repro, refactors inside one module. Most packets land here.

If you guessed low, you'll know: two fix-list rounds and it still hasn't landed. That's the signal to respawn on a stronger model and mark the old session superseded. The reverse signal is the first question again: if the acceptance could be a script, you're overpaying.

Pass the tier name (haiku / sonnet / opus). Relay resolves it through this machine's CLI, so nobody types a stale version id from memory.

Check the cheap case first, then the expensive one; Sonnet is what is left. The "two rounds" rule is the only feedback most people will actually use.

effort

Effort is how long it thinks before each action. It doesn't make a model smarter.

A Sonnet at max effort is a Sonnet that takes longer. Effort is a quality lever on top of the right model: turn it up (xhigh) only for an Opus executor whose whole job is finding root causes.

Don't turn it down to save money. Here's why:

prompt output one real executor session today: 5.1M prompt tokens, 29k output. Thinking lives inside that 29k.

Set per packet with an EFFORT: line or --effort. It's fixed for the process, and executors get reused, so you're setting it for every packet that session will ever see. Unset is the right default.

The bar is the argument. Output, thinking included, is under one percent of what the session cost. The lever people actually want is the model tier.

caching

Caching, in one minute

Claude has no memory between turns. Each turn, your whole conversation is sent to the API again, and billed again.

The cache is the API holding on to the start of that conversation for 60 minutes. Text it already holds costs 10% to send again. Text it has to store costs 125–200%, once.

Every turn resets the 60-minute clock. Go quiet for an hour and the whole history gets stored again, at the full storing price.

what's in it: the exact bytes of the request, from the start, in this order

system prompt
Claude Code + executor role + CLAUDE.md
tool
definitions
the packet
every file it read
tool results are part of the conversation
command output
its own replies
this turn
not held yet

Same system prompt, same zero-MCP tool list on every executor → that first stretch is shared between them. A file read on turn 3 is re-sent on every turn after, at 10%, but forever.

Beat one is the whole idea: no memory, so everything is re-sent. The strip shows what "everything" is. Point at "every file it read".

caching, turn by turn

Why a warm executor is cheap and a huge one isn't

turn 1
store system + packet
×1.25
turn 2
re-send turn 1 ×0.1
store the new part
turn 3
re-send 1–2 ×0.1
store the new part
… turn 40
re-send everything ×0.1
this is the 97% hit-rate
1 hour idle, turn 41
store everything again
×1.25–2 on the whole history

It's a prefix. Change anything early, whether the system prompt or an old message, and everything after it has to be stored again.

It's per model. Move the executor to Opus and you start from nothing.

Held isn't free. A 200k history still costs about 20k tokens' worth every single turn.

Most people think caching is a discount. It's the reason reusing a warm executor is cheap and a huge one is a tax on every turn, which is the next two slides.

The things that move the bill, biggest first:

  • Which tier. Multiples, not percents.
  • How much it reads per turn. Tight packets. No MCP servers by default; their tool lists would sit in every turn.
  • Warm reuse vs. cold spawn. Previous slide.
  • Past 200k of live context. Long-context pricing kicks in.
  • Effort. Last, and small.

reuse, rotate, hand off

Keep using an executor while it's cheap. Replace it when it isn't.

/relay:send puts a follow-up into an executor you already have. Warm cache, and it knows the codebase. Always the first choice over spawning.

Its live context grows with every turn. relay list shows it as CTX, with ·warm or ·cold~N beside the tokens. At 150k, relay send refuses:

session 'ctx-gate' is heavy — its live context is 264k tokens,
past the 150k nudge (long-context pricing starts at 200k) …
  --rotate           retire it, spawn a seeded successor, this packet first
  --heavy-override   send anyway; the reason goes in the ledger

what the old signal saw: transcript size

1.7 MB of a 5 MB threshold: "fine"

what the new signal saw: live context

264k against a 150k line: "rotate"

The executor that built this gate this afternoon was the first session it caught.

The lead has the same problem at a slower rate. Its statusline shows its own transcript size; past 5 MB relay nudges once: write a handoff note, /relay:handoff, and a fresh lead picks up with the note as context.

Rotate = retire the old one (it writes a successor seed indexing its packets and reports) and spawn a new one that reads the seed first. You lose the conversation, you keep the knowledge.

lifecycle

When executors close, and how

Landed

You committed (or discarded) its work, and the files it claimed are clean in the tree. Two minutes later relay closes the tab on its own.

Idle

It reported, you've seen the report, and 60 minutes passed. Closed.

By hand

/relay:close now. /relay:retire to close and write the successor seed. --keep at spawn, or relay keep, pins one you know you'll need.

Closed isn't gone. /relay:send to a closed session reopens the same conversation with everything it knew. /relay:resume does that for a tab that crashed. /relay:restart re-runs the packet in a fresh conversation when you'd rather it forgot.

Nothing is auto-closed until the lead has actually seen its report. Busy, stalled, queued and pinned sessions are never touched.

The question behind this slide is "will I lose work?" No: staged changes live in the worktree, reports live on disk, and the conversation is resumable.

guardrails

What stops a bad afternoon

The edit gate. Armed by /relay:mode. A lead that tries a large inline edit is blocked and told to delegate. Packet files are exempt. /relay:route retain "reason" opens a two-minute window when it really is lead work, with the reason in the ledger.

Announce and wait. By default, when the wake fires, the lead tells you what's ready and stops. /relay:auto on flips that to proceed-by-default inside a plan you already approved, and it resets each time lead mode is re-armed.

Committing needs all five, even in auto:

  • verify says COUNTS-MATCH
  • report says clean, risk flags none, unverified none
  • the packet was in the approved plan
  • nothing sign-off-gated is touched: core logic, ledgers, migrations, deploys
  • the lead has actually read the diff

The last two are the lead's own attestations. The tool can't check them, so it refuses unless they're passed. Passing them falsely is a false statement in the ledger, not a shortcut.

Today every commit stopped at the gate anyway, because the packets touched lib/lead_guard.py. That's the gate working.

using it

Six steps

/relay:modeArm the lead. Model check, edit gate on, wake on.
write a packetGoal on the first line, files, acceptance commands, boundaries.
/relay:spawnWorktree, topic, packet, --model sonnet. Or /relay:send into one you have.
waitThe wake announces the report. /relay:check if you're impatient.
/relay:diff /relay:verifyRead the diff. Check the claims.
git commitYou, not the executor. Then relay parks it.

The first spawn of a session always asks for your go, even in auto. Deciding how work splits is yours.
